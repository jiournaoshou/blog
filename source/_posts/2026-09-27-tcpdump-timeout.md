线上有一个内部接口，平时 P99 在 80ms 左右，但每隔几分钟会冒出一个 3 秒的超时。应用日志里只有一行 `dial tcp ...: i/o timeout`，上下游都说自己没问题。

这种情况靠看日志是查不出来的，得上抓包。

## 先缩小范围

先确认是哪一层的问题。三个探针分别打：

```bash
# 1. 纯 TCP 建连
time nc -zv 10.20.3.11 8080

# 2. HTTP，不带 body
curl -o /dev/null -s -w '%{time_connect} %{time_total}\n' http://10.20.3.11:8080/healthz

# 3. 同机不同端口，排除端口过滤
time nc -zv 10.20.3.11 22
```

结果很关键：**`curl` 的 `time_connect` 本身就占了 2.9 秒**，说明业务代码还没开始说话，卡在三次握手。范围一下从"应用"缩到了"网络"。

## 抓包

在出问题的机器上挂着抓，不落盘（超时是随机的，落盘再翻会很麻烦），对着终端看 `tcp.flags.syn` 就行：

```bash
tcpdump -i eth0 -nn -ttt 'host 10.20.3.11 and port 8080 and tcp[tcpflags] & tcp-syn != 0' -c 200
```

`-ttt` 让时间戳变成相对上一包，重传的间隔一眼就能看出来。抓了一会儿就看到了要的东西：

```text
 00:00:00.000000 IP 10.20.1.7.51432 > 10.20.3.11.8080: Flags [S], seq 4182937402, win 65535, length 0
 00:00:01.001243 IP 10.20.1.7.51432 > 10.20.3.11.8080: Flags [S], seq 4182937402, win 65535, length 0
 00:00:02.002891 IP 10.20.1.7.51432 > 10.20.3.11.8080: Flags [S], seq 4182937402, win 65535, length 0
 00:00:03.004506 IP 10.20.3.11.8080 > 10.20.1.7.51432: Flags [S.], ack 4182937403, win 28960, length 0
```

典型的 SYN 重传：客户端发了三次 SYN，每次间隔正好 1 秒，服务端在第三次之后才回 SYN-ACK。超时是 3 秒，所以客户端在收到应答前就先放弃了。

## 为什么 SYN 会丢

SYN 丢失通常只有几种可能：**服务端 accept 队列满**、**中间设备丢包**、**服务端的 conntrack 表满**。

先在服务端看半连接队列：

```bash
ss -lnt sport = :8080
nstat -az | grep -E 'ListenOverflows|ListenDrops'
```

`ListenOverflows` 是 0，排除了队列问题。服务端和应用都没问题。

再查客户端方向的丢包：

```bash
netstat -s | grep -i -E 'retrans|drop'
ip -s link show eth0
```

`eth0` 的 RX dropped 有缓慢增长。到这一步就不该再猜了，去问网络组：那台机器所在的机柜，最近上游设备有没有动过。

答案是：上周换了机房的一台接入交换机。型号很老，MAC 地址表容量不够，而那个网段里有一批容器在频繁抖动、不断更换 MAC，把表刷满了。新 MAC 走泛洪，运气好的时候能到服务端，运气不好就丢了——正好对应"偶尔"这个特征。

## 结论和办法

1. 短期：把服务端换到另一个网段，SYN 丢失消失。
2. 长期：让容器固定 MAC 的生成方式（有些 CNI 用随机 MAC），把交换机也换掉。

这次最有用的其实不是 `tcpdump` 本身，而是**先做三次探测、把问题定在"建连阶段"**这一步。如果一开始就去翻应用的 goroutine dump，很可能查到半夜。

## 以后再遇到类似问题

给自己留一份检查顺序，省得每次重新想：

1. `time_connect` 和 `time_total` 分别多少？先定层。
2. `tcpdump` 看 SYN 有没有重传，间隔是不是 1s / 2s / 4s。
3. 服务端 `ss`、`nstat` 看队列和丢弃。
4. 客户端 `netstat -s`、`ip -s link` 看重传和丢包。
5. 以上都正常，去问物理世界：换过什么设备、打过什么补丁、那天有没有人重启过什么东西。

最后一条往往最有效。
