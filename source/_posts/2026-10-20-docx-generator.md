组织部每学期要收几百份《班会记录表》和《团日活动记录表》。要求不是"大致规范"——是精确到 `w:sz="30"`、`w:spacing="-20"`、`kern=0` 共 27 处的那种规范。各班交上来的，标题序号混用、分点挤成一段、照片尺寸不一、落款位置各异。

手工改能撑一时，撑不了一学期。所以这东西最后变成了两个工具：

- **班会记录生成器** —— 拖进任意班的原件 docx，输出可直接上交的成品
- **团日活动记录表生成器** —— 网页版，带密码门，部署在公网

## 问题不在"生成一个文档"

如果只是按模板填内容，`python-docx` 二十分钟就能写完。真正的麻烦是**理解一份"合格的表格"到底由什么构成**。

学院给了一份优秀样本当母版。逆向它的结果是这样的：

| 项目 | 精确要求 |
|---|---|
| 表格 | 7 行，列宽 4589 + 4814 = 9403 twips，**故意宽于页边距** |
| 行高 | 426/446/407/446/574/678/6764，全部 `hRule=atLeast` |
| 字体 | 大标题黑体 22pt，表格内仿宋 14pt，**全文不加粗** |
| 字距 | 前 8 个信息段的每个 run 都要 `spacing=-20`，共 **19** 处 |
| 字距 | 「主题」段的强调文字 `spacing=-8`，共 **3** 处 |
| 字距 | 其余正文不写，多写一处都不合规 |
| 字距 | `kern=0` 共 **27** 处 = run 级 19 + 段落标记级 8 |

最后那条 `kern=0` 是最容易漏的。它有两个层级：`w:rPr/w:kern` 和 `w:pPr/w:rPr/w:kern`，也就是 run 本身和段落标记各算一次。只做 run 级，数字对出来是 19，不是 27。

这种数量级的校验项，肉眼查不出来，只能写成脚本逐个断言。

## 第一个真正的坑：下划线不显示

`rPr` 的子元素顺序是 OOXML 规定死的：

```
rFonts → b → bCs → … → color → sz → szCs → u → … → lang
```

`<w:u>` 必须排在 `szCs` **之后**。有一次它被写在了 `color` 前面，Word 一声不吭，下划线就是不出现。没有报错，没有警告，渲染出来「记录人：孙泽晨」干干净净，就是没线。

改完顺序才想起来，这是规范里的硬约束，不是"建议"。

## 第二个：照片尺寸差 0.09 毫米

照片规定 14×7cm 嵌入。`python-docx` 写图的时候会产生舍入误差，实际落下来是 `5039995 × 2519680` 而不是 `5040000 × 2520000`。

差 0.09 毫米——肉眼绝对看不出来。但校验项要求精确值，所以每次生成后都要把 `wp:extent` 和所有 `a:ext` 强制改回去。

还有一次，为了修跨页把照片从 14×7 缩成 10×5，被要求改回来了。教训记在文档里：**排版问题靠调正文长度解决，不要动照片尺寸。**

## 第三个：`cantSplit` 让整页只剩表头

表格第 6 行一开始设了"禁止跨页"（`cantSplit`）。当内容本来就超过一页时，Word 会把这一整行推到下一页，第 1 页就只剩表头和大片空白，跨页处的边框还断了。

正确做法是移除 `cantSplit`，让内容自然跨页。

这里还有个反直觉的地方：**"多了一页"不一定是 bug**。有一次看到输出变成两页就去找分页符，最后用 PDF 数了各页的文本操作符才确认——就是内容量自然越过了分页边界。所以判断标准是"有没有空白页"，不是"是不是一页"。

## 最难的部分：判断"这段到底是不是标题"

上面的都是格式问题，有标准答案。真正花时间的是内容理解。

各班交上来的原件里，分标题和正文经常挤在一段：

```
（一）开场导入班长传达学校《关于做好中秋国庆假期安全工作的通知》…
```

整段超过 26 个字，如果按"长度超了就整行删"处理，标题会丢、内容会糊。要拆对，得同时满足好几个信号：

1. 序号后 26 字内出现标点，且标点前是个名词性短语（以「专题 / 教育 / 管理 / 导入 / 小结」这类词收尾）
2. 标题后面紧跟正文主语的开头（`班长` / `全体同学` / `提醒` / `落实` / `假期`…）
3. 反过来，`1.落实学校…要求，开展…` 这种**带谓语的长句**不能当标题

还有三种粘法都要处理：标题在前、标题在后（`…不擅自旷课、晚归。（六）班会小结`）、以及一个标题里内嵌多个子点。

原则是**两条都不满足就不拆**——宁可不拆，也别误伤正文。自动化的风险从来不是做得不够，是做得过火。

## 缩进规则改过三次

母版自带的缩进是旧规则。后来改成：只有「一、二、三、四、」这种一级标题顶格，其余段落全部空两格。

写 `w:ind` 的时候必须**先清空原有的全部属性**再设新值。否则模板残留的 `firstLineChars` 会和新的 `firstLine` 打架，渲染出乱值。

还有个更隐蔽的：`python-docx` 读 `first_line_indent` 做校验时会失真，`firstLineChars` 换算出来是 225806000 这种数字。要校验缩进，**必须直接读 XML 里的 `w:firstLine`**。

## 网页版：docx 在浏览器里拆开

团日那个工具做成了单文件 HTML，同学自己在浏览器里用。核心是用 `JSZip` 把 docx 当 zip 拆开，改里面的 XML 再打包回去。全程在本地，文件不出机器。

同类的问题又踩了一遍，还多了几个网页特有的：

- **密码框不能用 `type="password"`**。部分浏览器的密码管理器会接管输入框，导致中文输入法直接打不了字。改成 `type="text"` 加 `-webkit-text-security: disc` 才行。回车提交还得排除输入法组合状态，否则拼音选字时按回车就误提交了。
- **`XMLSerializer` 本身会输出 XML 声明**，如果代码里再手动加一条，就是重复声明，WPS 打不开文件。
- **`[Content_Types].xml` 里要补 jpg 声明**，否则图片打不开，Word 直接报文件已损坏。
- **每张图片要独立 `rId`**，共用的话两张照片会显示成同一张。

## 打包成 exe 之后又崩了

用 PyInstaller 打包成双击即用的 exe，加了 `--noconsole`。结果双击就崩：

```
'NoneType' object has no attribute 'buffer'
```

因为没有控制台时 `sys.stdout` 是 `None`，而代码里愉快地访问了 `sys.stdout.buffer`。得先判断 `sys.stdout is not None`，无控制台时把输出写到日志文件。

还有一次漏带了 tkinter，状态小窗 import 失败，用户既看不到程序在干什么也关不掉它。打包要加 `--hidden-import tkinter`。

## 最贵的一课：验证脚本把照片弄丢了

有一条比较严重：写验证脚本的时候，正文是手工抄的、`photos` 字段直接写死了 `[]`。脚本生成的"无照片文件"覆盖掉了真的成品——**照片全丢**。

教训是：验证脚本不能造假数据，尤其不能把"缺失"当默认值写死。

同类还有一条：`title` 用 A 班会的原件去套 B 班会的内容，目的段和正文完全对不上。所以工具里定了一条硬规则——目的段只能从原件正文里读，原件写什么就是什么。

## 业务侧的坑，比技术坑更致命

技术上的坑最多让人返工，业务上踩坑是直接打回。组织部的规定里有几条特别容易被忽略：

| 会被打回的情况 | 说明 |
|---|---|
| 文档里有看不见的空格、手动回车 | 审批用"显示空格标记"逐个揪 |
| 行距被改成 1.5 / 2.0 | 为写满一页偷偷加的，必须改回单倍 |
| 两个班共用同一张照片 | 哪怕同一个班主任也不行，一律补拍 |
| 拿团日总结套班会总结 | 两者模板不同，班会 5 板块 / 团日 7 板块 |

第三条尤其值得单独说：**不得以"以前没这要求"推脱**。规范升级之后，旧成品不能拿来当依据。

## 现在它在做什么

工具跑起来的流程是这样的：

```bash
# 拖入原件 → 提取字段 → 清洗正文 → 填表 → 校验
& $py "生成器\_build_from_source.py" "原件.docx" "成品.docx"

# 按 v3 标准逐项校验
& $py "生成器\标准\check_against_v3.py" "成品.docx"
```

校验期望值是写死在脚本里的：表格 7 行 / `spacing-20` = 19 / `spacing-8` = 3 / `kern=0` = 27 / `tcBorders` = 9 / 图片 14×7cm / 概述 ≤15 字。数字对不上就说明哪一步错了。

网页版还配了个反馈系统：同学在右下角点反馈，写进 Supabase，后台 exe 每 15 秒刷新一次，新反馈高亮。没配云数据库也能用，反馈先存浏览器本地，配好后自动补发。

## 写完之后的想法

这类工具的价值不在"能不能做出来"，在**能不能让人放心地用它交差**。

格式规范里的每一条数字（19、3、27），背后都是一次被打回的返工。把它写成校验脚本，等于把"记得检查这些"这件事从人的脑子里挪进了代码里。人可能会忘，脚本不会——前提是脚本是对的，而这一点本身也踩过坑。

两个项目加起来，`团日材料` 里 20 个脚本、`班会记录工具` 里 40 多个文件，最长的那个 `交接文档.md` 有 770 行。真正花时间的不是写代码，是**把"什么算合格"这件事搞清楚，并且写下来**。

第 25 条教训是：中文的 `.gitignore` 规则没生效，最后靠把无关目录物理移出项目、重建索引才解决。这种经验写不进任何教程，只能自己撞一次。
